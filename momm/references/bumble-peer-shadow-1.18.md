## Components

- `review-contract-schema.mjs`: the single generation hint shared with the
  existing CLI dispatcher. It encodes structure, not a required verdict.
- `bumble-peer-review.mjs`: bounded request construction and strict validation
  using the actual peer contract's quotation normalization and semantic checks.
  Transport, parsing, schema, scope and finding accuracy remain separate gates.
- `bumble-peer-worker.mjs`: proposed supervised Windows protected-file/TLS
  worker. The key is read only inside that process and placed only in the pinned
  HTTPS header, never its stdin/argv, prompt, result or evidence. Unsupported
  storage platforms refuse; tests do not certify native macOS/Linux storage.
- `bumble-peer-shadow.mjs`: the trusted governor-host seam. It accepts the
  existing `runProcess` and shared `BumbleCapacity`; it creates no dispatcher,
  capacity map, credential store, baseline or approval authority itself.
- `bumble-native.mjs`: exposes that preparation seam while keeping normal native
  entry closed, before dereferencing unapproved caller credentials or hooks.

Only governor-selected synthetic source is permitted in this initial scope.
Private repositories need separate disclosure/approval. Provider, endpoint,
model/build/profile, model family, role/version, session and attempt identities
must be kept distinct. Unknown family adds no independent-family vote; shadow
output always has zero release-quorum votes regardless of verdict.

## Host obligations before live use

Bind a protected owner receipt to the exact connection and certificate, credential
epoch, adapter/contract/schema/role identity, disclosure, finite budget and actual
operator reconciliation evidence. Verify those records; do not invent a receipt
from source comments, model output or an idle-slots response. Pass the existing
supervisor and owner-global capacity manager; never construct a new ledger or
alter an old configuration to escape refused admission.

The host receipt must now bind an authorization digest and the existing capacity
configuration digest. The seam passes the four-attempt/4,096-token/1,024-token
per-request ceiling into the existing manager's atomic `reserve`, not merely a
preliminary `summary` check. Scoped terms are retained with each reservation and
must remain identical across restarts. Charges include known-unsent outcomes;
they do not reset or permit retries. One outstanding reservation is the initial
ceiling, and module-owned time prevents caller-clock expiry bypass for this scoped
path. Every older global/resource/source-IP limit still applies. No existing
configuration is widened, old store migrated or separate capacity ledger created.
Scoped transmission and terminal validation also use module-owned time inside
the lock. A backdated caller timestamp cannot mark an expired request as sent
or turn a response after its deadline into a valid timely result. Legacy
unscoped clock behavior and all stored historical outcomes remain unchanged.
Matching digests do not authenticate a receipt's origin; the protected host must
still verify provenance and select the existing owner-global manager before live
use. A synthetic fixture is not permission to create a fresh real admission store.

The shadow seam captures the sent artifact before awaiting the child and validates
all child result fields before persisting metadata. Invalid child output keeps
the reservation held. Transport/payload combinations must agree, and child
duration cannot exceed the approved 180-second ceiling. Malformed JSON or
credential reflection remains a payload failure even if HTTP transport finished.
Governor-run regressions reproduce host precondition,
metadata and artifact-mutation failures on the earlier source, then pass on the
fixed source. These local observations do not replace independent source review.

Persist the attempt identity before transmitting and preserve both success and
failure records. Unknown child execution, socket errors, incomplete body, timeout
or credential reflection stays held and cannot replay. Authentication errors and
429 refusals remain explicit; Retry-After is recorded, not an automatic retry.
A gateway 5xx reply (for example 502 or 504) is not a refusal: the backend may
still be running, so it stays `outcome_unknown` with payload `upstream_error`
and the original HTTP status and request ID recorded, and the hold is retained.

The worker refuses UNC, device and alternate-stream material-path spellings before
filesystem access. A drive-letter path alone is not proof of a local disk; mapped
drives and full filesystem qualification remain separate gates. Terminal cleanup
claims its result before destroying sockets so synchronous abort events cannot
replace an overflow/deadline classification. The shadow coordinator rechecks its
absolute deadline immediately before launching the child; local evidence work
cannot manufacture a fresh one-millisecond allowance after expiry. Such an expired
marked reservation stays held and is recorded outcome-unknown, not physically released.

The default capacity component retains a transmitted reservation even after a
valid complete response. A 15 October development component adds explicit
`releaseChallenge`/`reconcileRelease` accounting with an owner-host verification
key pinned separately from receipt data. The receipt binds the exact original
reservation/configuration, backend terminal state and physical lease release;
Ed25519 verifies the signed UTF-8 payload, not the truth of the host's observation.
This is an internal host-attestation format, not an assertion that BAB exposes
signed receipts or a request to change BAB. No signer, private key, owner trust
choice, live evidence or protected broker is created by the verifier.

Stored proof is checked again on restart against the same configured key;
missing pins, changed/foreign receipts and gateway cancellation without a lease
refuse. Release does not relabel the original result or refund attempt/token
charges. Only fresh evidence is admitted; accepted historical proof stays
historical rather than expiring a released slot.

On backward host-clock steps that make recorded observations appear future-dated,
the store intentionally refuses further operations for manual reconciliation;
it neither rewrites timestamps nor guesses that held jobs have ended.
Existing supplementary-stage
state still needs separately qualified cross-store adoption, and no normal native
path calls this component. The seam cannot perform a live batch without the
qualified host/status/release path. Do not reinterpret completion as lease release.

Implementation reference: [Node22 crypto verification](https://nodejs.org/download/release/v22.16.0/docs/api/crypto.html#cryptoverifyalgorithm-data-key-signature-callback).

Normal pipeline integration still needs the protected host/broker and sealed
independent-baseline-first stage wiring. Merely importing the seam does not
complete those components or activate it in the ordinary dispatcher.
