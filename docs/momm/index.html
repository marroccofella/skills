◆ MOMM · local multi-CLI code review with a reproduction gate · v1.14.0

Have the other AI CLIs on your machine review your diff. Then make your agent prove a finding before it fixes it.

MOMM is one Node script, installed as an Agent Skill. Your coding agent pipes a diff, a document, or an attached file to whichever of Codex, Claude Code, Antigravity, GitHub Copilot and Grok are already logged in on the machine. They review in parallel, read-only. Their output is treated as untrusted data. Your agent stays the only writer, has to reproduce a finding before it changes anything, and records what it did with every suggestion. Every run is logged locally with content hashes.

Preview, then run it again without --dry-run. The installer writes into the harness you name (claude, codex, gemini, antigravity) and refuses to guess. --target all exists; you have to type it. Then tell your agent “use momm to review my current changes.” Or paste this into any agent:

Install the momm skill from https://github.com/marroccofella/skills: clone it, run `node install.mjs --target <this harness>`, then `node momm/scripts/multi-review.mjs --preflight --governor <you>` and tell me which routes are logged in. Then use momm to review my current changes and follow momm/SKILL.md: reproduce a finding before fixing it, and end with the table of what you applied and rejected.

What leaves your machine: each route you run sends the redacted, metadata-stripped input to that vendor over your own login. That is the review. Nothing else is sent; this page sends nothing. “No API keys” is how it authenticates, not a privacy property.

What it does

Four rules, one script.

  • Fan out. Send the artifact to every other installed CLI at once, over each one's own login. Missing or logged-out routes are reported and skipped.
  • The writer does not grade its own diff. The agent running the review is excluded from reviewing. Reviewers cannot write, commit, or run tools.
  • Nothing changes until it reproduces. A finding is a claim. The agent has to write a failing reproduction before it authors a fix, and rejects on the record what it cannot reproduce.
  • Keep the transcripts. Each run's report is stored locally with a sha256 over its bytes and the hash of the exact input, next to a log of what the agent applied and rejected and why.

Honest accounting of what is new here: fan-out to several models is common (mixture-of-agents, multi-reviewer prompts). The parts worth keeping are the reproduction gate, the writer's self-exclusion, and the logged dispositions — plain engineering hygiene, written down as a protocol an agent actually follows, with the logs to check it did.

How it works

One writer. Several read-only reviewers. A gate between them.

When to use it

Not on every save.

◈Staged commit · --tier quick

The two fastest routes with a 60-second budget. A second and third opinion on a diff before you commit it.

◈Release gate · --tier deep

Every logged-in route, quorum of two, budgets that scale with input size. This is what caught the supervisor bug below. Expect two to five minutes and the odd timeout.

◈What it costs

Whatever subscriptions you already have. It does not need all five; it needs one. Each extra route is more time and another vendor seeing the input.

◈What it does not do

It will not auto-apply anything, and it will not run reviewer-supplied code. The reproduction is still the agent's (or your) work — that is the point, and it is also why quick reviews should stay small.

Documents

It reads prose too. Treat that as experimental.

Pass a manuscript or any text with --input, a PDF or figure with --attach (Codex and Claude read images; Claude and Gemini read PDFs), and put your own review guidelines in a .reviewrules file — every route receives them. The shape is the same as code review: several independent readers, a gate before anything is acted on, a record of what was decided.

Get started

Three commands.

  1. Clone and link into the harness you use (preview with --dry-run first; the installer will not guess):

    git clone https://github.com/marroccofella/skills && cd skills && node install.mjs --target claude

  2. Check every route — zero model calls; prints the exact install or login command for anything that is down:

    node momm/scripts/multi-review.mjs --preflight --governor claude --pretty

  3. Review your changes, quick or deep. Your local dashboard is one more command: node momm/scripts/ledger.mjs --open

    git diff HEAD | node momm/scripts/multi-review.mjs --governor claude --tier quick git diff HEAD | node momm/scripts/multi-review.mjs --governor claude --tier deep --pretty

A .reviewrules file at the repo root is injected into every reviewer's prompt. Every run prints its version and checks once a day for a newer release (a cached GET of versions.json; NO_UPDATE_CHECK=1 disables it). The dispatcher is a single dependency-free Node 18+ script with 61 self-tests, plus a CI matrix across three operating systems and three Node versions. Read the source.

FAQ

Does it send my code anywhere?

Yes. Each route you run sends the redacted, metadata-stripped input to that vendor — OpenAI, Anthropic, Google, GitHub or xAI — over your own CLI login. Nothing else is sent. Setup and preflight read no credentials and make no model calls; the Setup Center's optional connectivity test speaks one disclosed synthetic sentence.

Do I need all five CLIs?

No. One logged-in external route is enough; the rest are reported as missing or logged out and skipped. --min-success lets a release gate insist on a quorum.

What if a reviewer is wrong?

It fails reproduction and is rejected with the attempt as the reason. That happened to a CRITICAL claim on this release. Its acceptance rate falls, and single-source findings from low-acceptance routes are flagged to reproduce first.

Which harness can drive it?

Any of codex, claude, gemini, antigravity, copilot, grok, or “other”. The driving harness is excluded from the reviewer pool for that run.

Can I run it in CI?

Yes — --strict and --min-success give non-zero exits; --stream puts NDJSON events on stderr with the report alone on stdout. Routes need network access and their CLI token stores, which restricted sandboxes usually block.

Is the walkthrough voice real?

It is a synthetic clone of the creator's own voice, generated locally with recorded consent and checked for signal health and word accuracy. It is labeled as synthetic wherever it is shared.
